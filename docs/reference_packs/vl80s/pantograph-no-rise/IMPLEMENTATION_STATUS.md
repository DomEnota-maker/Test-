# Integration status — Diagnostic Framework v2

The Test branch uses this pack as an overlay on the canonical technical objects and the diagnostic graph. The module's `referencePackAsset` field selects the pack; adding another module and pack does not require a scenario-specific branch in the loader. `app/` and `patch/app/` mirror the runtime files.

## Acceptance mapping

- 19 knowledge entries, 12 source records, and 3 conflict groups are parsed and validated. Source, component, direction, related-entry, and conflict references must resolve.
- BASIC/EXTENDED knowledge mode, MINIMAL/STANDARD/DETAILED depth, and the separate extended-emergency gate are independent. Restricted field/unsafe entries require EXTENDED, DETAILED, study view, and the gate; their procedure payload is absent.
- The immutable answer trail reorders directions and visible entries. A single-versus-all observation raises the local or common branch, and an observed air release raises the pneumatic branch; the separate leak question does not infer its location or cause. `UNKNOWN` preserves alternatives.
- The card displays human-readable titles, confidence, variant caveats, limitations, conflict notes, source titles, and Atlas links. Internal identifiers are not rendered.
- The study view progressively reveals six levels of the selected canonical object. Detailed entries show applicability conditions and a human-readable use status.
- An additional profile fixture resolves a TEM2 equipment object directly from its existing Atlas catalog, and the shared diagnostics selector routes framework modules by catalog profile. No TEM2 diagnostic content is shipped by that fixture.
- Android acceptance captures all six mode/depth combinations, six object levels, and restricted-gate off/on behavior, alongside beginner, expert, study, and diesel-diagram navigation. Unit tests cover the same axes and data-driven routing.
